# Example — `arch-crew:test-patterns`, review: a RAG support agent

A team with an LLM in the call path tends to buy an eval harness and stop. This review keeps four
things apart that were merged into one number: deterministic scaffolding, retrieval quality, semantic
answer quality, and the trustworthiness of the instrument doing the measuring.

## Scenario

A customer-support agent over a 40,000-document knowledge base. It retrieves passages, answers, and
can call three tools: `lookup_order`, `issue_refund` (capped, and irreversible), and `escalate`.
Deployed to real customers. The team has an eval suite and a single dashboard number — "answer
quality: 8.3/10" — produced by a GPT-class judge.

## User prompt

> "Review this RAG agent's tests and evaluations. Separate deterministic software evidence from
> stochastic evaluation. Review only — don't change any files."

The read-only request is honored: the review below is presented in full, and nothing is written to
the repository.

## Repository observations

- `tests/` contains 31 tests. **28 of them call the real model** and assert on substrings of the
  answer (`assert "refund" in response.lower()`). Marked `@pytest.mark.flaky(reruns=5)`.
- **No test covers tool dispatch, tool argument construction, or the permission check on
  `issue_refund`.** The refund cap is enforced by a single `if` in `tools/refund.py` with no test.
- `evals/cases.yaml` holds 120 cases. `evals/README.md`: "generated with GPT-4 from the docs".
  No record of human review.
- The judge prompt lives in `evals/judge.py` and uses **the same model and system-prompt style** as
  the agent itself. No calibration set, no human-labelled examples, threshold `>= 7.0` — set, per the
  commit message, "to match our first run".
- No retrieval metric anywhere. When an answer scores badly, nobody can tell a retrieval miss from a
  generation failure.
- Production logging captures latency and cost. Nothing captures refusal rate, escalation rate, or
  answers produced with zero retrieved passages.
- Two escaped incidents: a refund issued above the cap (a wiring defect — the cap check ran *after*
  the provider call), and a fortnight of degraded answers after a re-chunking deploy that nobody
  noticed.

Both incidents are diagnostic. Neither was a semantic-quality failure, and neither would have been
caught by a better judge.

## Observed current portfolio

deterministic scaffold tests **3** (31 minus the 28 that hit the model) · retrieval evaluation **0** ·
semantic evaluation 120 unreviewed cases behind one uncalibrated judge · production signals: latency
and cost only. Shape: **evaluation-heavy overlay with no deterministic base** — the anti-pattern the
catalog names as "an eval suite with no deterministic tests underneath it".

## Evidence-placement problems

1. **The deterministic half is untested.** Tool dispatch, argument construction, the refund cap, the
   escalation path, and output parsing are all deterministic code — and none of it is asserted. The
   over-cap refund was an ordering bug in `tools/refund.py`. A three-line unit test would have caught
   it; no volume of evals ever would.
2. **Unit tests call a real provider.** 28 tests are slow, billed, nondeterministic, and papered over
   with `reruns=5`. They also assert exact substrings on stochastic output — permanently flaky by
   construction.
3. **The eval set has no oracle.** 120 cases generated by a model from the docs, never reviewed.
   They encode whatever the generator believed; a wrong belief is now a passing test. This is the
   generated-oracle defect wearing an eval costume.
4. **The judge is an unvalidated instrument used as ground truth.** No calibration against
   human-labelled examples, no agreement rate, a threshold set to whatever the first run produced,
   and it shares a model and prompt style with the system under test — a documented self-preference
   risk. "8.3/10" is a number with no known relationship to customer experience.
5. **Retrieval is invisible.** The re-chunking incident is exactly the failure a retrieval metric
   exposes and an end-to-end answer score hides. Fourteen days of degradation went unnoticed because
   no signal separated the two failure modes.

## The single highest-leverage move

> **Build the deterministic scaffold test layer — tool dispatch, argument construction, the
> `issue_refund` cap and permission check, escalation, output parsing, retries — with the provider
> suppressed, and move the 28 model-calling tests out of `tests/` into the eval set where they
> belong.**

This is first not because retrieval and judge calibration do not matter — they do, and they are next
— but because **the only two incidents that actually reached customers were deterministic defects**,
the fix is hours rather than weeks, and it removes the flakiness that currently makes the whole suite
untrustworthy. An irreversible action guarded by an untested `if` is the largest exposure in the
repository.

**Expected benefit:** the class of defect that caused the over-cap refund gets evidence for the first
time; `tests/` becomes fast, free, and deterministic; `reruns=5` disappears; and the eval suite stops
being asked to do a unit test's job.

**Migration scope:** a seam to inject a deterministic test model (in PydanticAI, `TestModel` /
`FunctionModel` / `Agent.override`, plus `ALLOW_MODEL_REQUESTS = False` at module level; other stacks
have equivalents). Smallest safe first step: **one test asserting `issue_refund` refuses an
over-cap amount, and one asserting the cap is checked before the provider call.** The second is
expected to fail today.

**Indicators the change worked:** tests calling a real provider (currently 28 → target 0); suite
runtime and cost; `reruns` removed; and the refund cap having a regression test attached to the
incident.

## Then, in order

1. **Add retrieval evaluation.** A labelled set of query → known-relevant-document pairs; measure
   recall and the rank of the first relevant hit, and count answers generated with zero retrieved
   passages. This separates retrieval misses from generation failures and would have surfaced the
   re-chunking regression within a day.
2. **Fix the eval set's oracle.** Have a support engineer review the 120 generated cases, keep what
   is right, correct what is wrong, and record who reviewed them and when. Add the two incidents as
   cases — a bug report is a specification. A reviewed set of 40 beats an unreviewed 120.
3. **Calibrate the judge, or narrow it.** Before it is trusted: a named claim ("is the answer
   supported by the retrieved passages?" rather than "quality"), 50–100 human-labelled examples, a
   recorded agreement rate, and a different model from the one under test. Move everything
   deterministically checkable — citation presence, refusal detection, schema validity, tool called
   with the right arguments — to deterministic evaluators first; a judge should only score the
   residue.
4. **Add production signals** for refusal rate, escalation rate, and zero-retrieval answers, routed
   to a named owner. A deployed stochastic system needs both pre-release evidence and monitoring;
   neither substitutes for the other.
5. **Add scenario evaluation** for multi-step task completion — but only once the dispatch and
   permission tests exist to diagnose what a failing trajectory means.

## Sound as-is

The tool interfaces are cleanly separated and easy to test — the seam is already there, unused. The
decision to log latency and cost from day one is right and rare. And the instinct to build an eval
suite was correct; it was simply built on nothing.

## Deliberately omitted from the recommendation

- **A bigger eval set.** 120 unreviewed cases are not improved by 500 more. Review beats volume.
- **A second judge to check the first.** Two uncalibrated instruments do not make one calibrated one.
- **E2E browser journeys.** No browser; no named journey whose failure needs full wiring beyond what
  the scenario evals will cover.
- **Fine-tuning or model changes.** Neither incident was a model-quality failure.

## Reopening signals

The agent gains autonomy over more irreversible actions → human-in-the-loop design (hand off to
`agentic-patterns`) plus permission tests per action. The corpus changes ownership or grows →
retrieval evaluation becomes a CI gate rather than a periodic check. Answer quality becomes a
contractual claim → the judge needs calibration evidence retained as an artifact.

## Generated-test oracle assessment

`evals/cases.yaml` — 120 cases generated by a model from the documentation, never human-reviewed —
has no independent oracle: the source of intended behavior is the same class of system being tested.
The judge is uncalibrated, shares a model and prompt style with the system under test, and its
threshold was set to match its own first run. Neither may be treated as ground truth until reviewed
and calibrated.

model-calling tests into the eval set.
